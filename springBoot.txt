Q) What is an ORM?

- ORM (Object-Relational Mapping) is just a fancy way of saying "Automatic Translation."

- Mapping literally means:

  This Class = This Table.

  This Variable = This Column.

  This Object = This Row. 


- JPA (The Specification)

   In CS, a Specification is a document or a set of rules (like an Interface in Java). It defines "what" should be done, but it doesn't provide the "how."

   JPA is just a collection of Interfaces and Annotations (like @Entity, @Id, @Table).

   It defines a standard way to map a Java Class to a Relational Table.

   Crucial Point: JPA cannot run by itself. It needs a "Provider" (an Implementation) like Hibernate to actually do the work.

   Analogy: JPA is the Interface; Hibernate is the Class that implements it.


- Spring Data JPA provides the Logic.

- logger.debug("The user " + user.getName() + " has " + user.getOrders().size() + " orders.");

Work: The JVM calculates user.getName(), fetches the order list, gets the size, and builds a brand new string in memory.

Check: The Logger looks at the level and says, "Oh, I'm set to INFO. I don't need this DEBUG message."

Result: The Logger throws the string away. You did all that CPU and memory work for absolutely nothing.


- logger.debug("The user {} has {} orders.", user.getName(), user.getOrders().size());

Check: The Logger looks at the level first. "I'm set to INFO. I'm ignoring DEBUG."

Result: The Logger stops immediately. It never looks at user.getName() or the order list. It never builds the string. No extra memory was used, and no CPU 
cycles were wasted.


Note: Plus in prod debug statements are never executed hence if debug is enabled in your code in prod you are wasting cpu cycles in doing something absolutely un-
necessary

Behind the Scenes: The SMTP Handshake
When you call mailSender.send(), a literal conversation happens between your server and the mail server (e.g., Gmail). It looks like this:

HELO/EHLO: Your app introduces itself: "Hello, I am myapp.com."

STARTTLS: Your app says: "Let's speak in code (encryption)." The server agrees.

AUTH LOGIN: Your app sends the username and password (Base64 encoded).

MAIL FROM: "I want to send an email from ujjwal@example.com."

RCPT TO: "Please deliver this to friend@example.com."

DATA: Your app sends the actual headers (Subject, Date) and
the body.

QUIT: The connection is closed.



InputStream (Reading): Data is flowing INTO your program.

Example: You are reading a file from the hard drive. The data flows from the disk into your Java code.

OutputStream (Writing): Data is flowing OUT of your program.

Example: You are creating an Excel file. Your program generates the data and "pushes" it out to a file or a network.


Point 4: The Spring "Resource" Interface
Now, let's look at Spring. In a professional application, your data could be stored in many places:

On the Hard Drive (File).

Spring created the Resource interface so you don't have to write different code for each one. A Resource is basically a "Handle" or a "Pointer" to data, 
no matter where it lives.

The Logic:Your Code: "Here is a FileSystemResource at this path.

ByteArrayOutputStream and ByteArrayInputStream

But these two classes are special: the destination is a Byte Array (byte[]) in your computer's RAM.

You use a ByteArrayOutputStream to "catch" the generated report in memory. Then, you use a ByteArrayInputStream to "read" that data so you can send it 
as an email attachment.

// 1. Create the "Bucket"
ByteArrayOutputStream baos = new ByteArrayOutputStream();

// 2. Write data (the "write" method fills the internal buf[])
baos.write("Hello Ujjwal".getBytes());

// 3. Extract the final array
byte[] finalResult = baos.toByteArray();



ByteArrayInputStream:

When you create this stream, you must provide an existing byte array: new ByteArrayInputStream(myBytes).
Inside, it keeps a "Cursor" (an integer variable usually called pos).

How it works "Under the Hood":

- pos: An integer that starts at 0.

- read(): When you call this, the stream returns buf[pos] and then increments pos by 1 (pos++).

- available(): It simply subtracts the total length from the current pos.

- End of Stream: Once pos equals the length of the array, it returns -1, signaling that there is nothing left to read.

byte[] myData = "Ujjwal".getBytes();

// 1. Wrap the array in a stream
ByteArrayInputStream bais = new ByteArrayInputStream(myData);

// 2. Read the bytes one by one
int data;
while ((data = bais.read()) != -1) {
    System.out.print((char) data); // Outputs: Ujjwal
}

cron

 ┌───────────── Second (0 - 59)
 │ ┌───────────── Minute (0 - 59)
 │ │ ┌───────────── Hour (0 - 23)
 │ │ │ ┌───────────── Day of the Month (1 - 31)
 │ │ │ │ ┌───────────── Month (1 - 12 or JAN-DEC)
 │ │ │ │ │ ┌───────────── Day of the Week (0 - 7 or SUN-SAT) 
 │ │ │ │ │ │
 * * * * * *


* (Asterisk - "Every"): Means "every possible value" for that 
field. An * in the Minute field means every minute.

- (Hyphen - "Range"): Specifies a range. 10-12 in the Hour field
means 10 AM, 11 AM, and 12 PM.

/ (Slash - "Increment/Step"): Specifies increments. 0/15 in the 
Minute field means starting at minute 0, and triggering every 15 
minutes (0, 15, 30, 45).

, (Comma - "List"): Specifies a list of values. MON,WED,FRI in 
the Day of the Week field means Monday, Wednesday, and Friday.


The Paradox of * in Both Fields
Scenario A: The 10th of the month.

What you want: 0 0 8 10 * ? (Run on the 10th. Ignore the day of the week).

If you used *: 0 0 8 10 * *

The System's Brain: "Okay, rule 1: Run on the 10th. 
Rule 2: Run on EVERY day of the week (Monday, Tuesday, Wednesday.
..). Wait... the 10th is only ONE day of the week! I can't run 
on the 10th AND run every day of the week simultaneously! ERROR!"



Scenario B: Every Wednesday.

What you want: 0 0 8 ? * WED (Ignore the date. Run on Wednesdays).

If you used *: 0 0 8 * * WED

The System's Brain: "Okay, rule 1: Run on EVERY date of the
 month (1st, 2nd, 3rd...). Rule 2: Run only on Wednesdays. 
Wait... every date of the month isn't a Wednesday! Which rule 
do I prioritize? ERROR!"



- You cannot have an * (every) in both the Day-of-Month 
(field 4) and Day-of-Week (field 6) fields

The Priority Hierarchy (Order of Precedence)

When Spring Boot boots up, it looks for properties in a specific order. Anything higher up on this list will completely override anything lower down.

Command-Line Arguments (e.g., --spring.profiles.active=prod) — Highest Priority

JVM System Properties / VM Options (e.g., -Dspring.profiles.active=qa in IntelliJ)

OS Environment Variables

Application Properties outside of your packaged jar

Application Properties inside your packaged jar (e.g., src/main/resources/application.properties) — Lowest Priority
